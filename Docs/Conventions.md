# 文档维护约定

文档应让读者尽快找到答案，并能区分产品现状、开发计划和历史证据。

## 按用途放置

| 位置 | 内容 | 更新方式 |
| --- | --- | --- |
| 根目录 `README.md` | 当前已发布版本、产品入口和既有预告 | 保持简洁，链接到详细说明 |
| `Docs/Guides/` | 使用、安全、本地开发与扩展指南 | 随当前行为持续维护 |
| `Docs/Architecture/` | 当前模块职责、依赖和设计原则 | 随实际代码结构更新 |
| `Docs/Development/<version>/` | 在研版本的计划、基线和验收 | 区分目标、实现、已验证和待验证 |
| `Docs/Releases/<version>/` | 已发布版本的更新与交付记录 | 修正定位和勘误，保留历史事实 |
| `Docs/Archive/` | 更早的设计和审计索引 | 保留原结论与上下文 |

0.4.14–0.4.16 的既有审计与结转文件暂保留原始路径。这些路径受发布证据、校验脚本和历史引用共同使用；归档索引是阅读入口，不用重复复制正文。

## 写清楚事实

- 标明适用版本。开发分支的版本元数据与当前发布版本分别说明。
- 实现、测试、真实桌面操作和三平台 CI 是不同证据，不互相替代。
- 迁移时更新链接和源码定位，不批量改写旧版审计状态、日期或验收结论。
- 当前指南直接说明支持能力、配置位置和限制；未来方向单独表达，不提前许诺。
- 命令应可从仓库根目录执行；桌面能力使用 `tauri:dev`，前端预览使用 `dev`。
- 应用内更新记录以 `Src/Features/Settings/ChangelogData.ts` 为入口。开发条目使用 `isUnreleased: true`、空发布日期，不标为最新发布；发布时再统一版本、日期和 `isLatest`。
- 更新说明使用正式、具体的表述，说明实际行为与适用范围；测试数量、性能结论和平台支持必须有相应证据。

## 保持格式一致

每篇使用一个一级标题，按二级和三级标题组织内容。表格保持列数一致；列表使用 `-`；代码块注明语言并闭合。目录以 `README.md` 为入口，文件名表达内容而非临时工作状态。

优先使用相对链接连接仓库内文档和源码。链接到标题时检查锚点；移动文件后同步修改引用方，避免保留大量转发页。

## 提交前检查

```powershell
pnpm run check:docs
pnpm run test:docs
git diff --check
```

检查器覆盖 Git 纳入管理及未忽略的新 Markdown 文件，验证本地文件、路径大小写、标题锚点、GFM 表格和代码围栏，提前发现 Windows 上不易察觉的跨平台路径问题。外部网站可用性、文案准确性和截图仍需人工确认。
