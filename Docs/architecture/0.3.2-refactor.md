# Aurona Code 0.3.2 Architecture Refactor

## Baseline

The 0.3.2 work starts from the clean `0.3.1` `main` branch. The frontend type
check, Biome checks, desktop/material boundary checks, 31 frontend tests,
release smoke test, production frontend build, and Rust formatting check pass.

Rust tests and the Tauri build are currently blocked on this Windows machine
because the active shell cannot find the MSVC `cl.exe` and `link.exe` tools.
This is an environment prerequisite, not a source-code regression. Rust and
packaging results must remain marked unverified until the C++ Build Tools
environment is restored.

## Problems found

### Module coupling

- `AuronaEngine` owns rendering, cursor and selection behavior, editing,
  diagnostics, completion, hover, and direct editor/LSP synchronization.
- `EditorTab`, `AuronaEngine`, `EditorIPC`, the Rust Rope session, and
  `LspClient` each retain overlapping document content or version state.
- The file explorer owns the live workspace root while search, Git, terminal,
  settings, and LSP independently read the persisted workspace file.
- `Foundation/Desktop` prevents raw Tauri imports outside the adapter folder,
  but domain/UI modules can still call arbitrary command names through
  `invokeDesktop`.

### State management

- Zustand workbench state correctly owns tabs and panel selection, but document
  state is React component state rather than a domain model.
- Diagnostics exist only on the mounted editor and the Problems panel therefore
  cannot represent the full workspace.
- Service status, server capabilities, output channels, and process failures
  have no observable application model.

### IPC and error handling

- Most Rust commands return unstructured strings; only editor commands expose a
  structured desktop error.
- The current generic `aurona_bridge` is effectively a ping endpoint and is not
  a meaningful typed domain boundary.
- LSP stderr is discarded and many frontend failures are reported only through
  `console.error`.
- The application close path flushes recovery data but does not explicitly wait
  for graceful language-server shutdown before destroying the window.

### Editor services

- Editor changes call the Rust editor session and LSP independently. A failed or
  delayed call can leave the two replicas on different revisions.
- File open/save/close, recovery, dirty state, and LSP synchronization are
  coordinated by component effects.
- The current completion path does not consistently reject responses for an old
  document revision or cursor context.

### LSP

- Server commands are hard-coded and use shell wrappers or download-capable
  `npx` commands.
- Initialization always sends `rootUri: null`, does not retain server
  capabilities, and declares only a partial hard-coded capability set.
- The transport has no reusable streaming decoder, no bounded headers/messages,
  no stderr capture, no server-request responses, and no observable lifecycle
  state.
- JSON-RPC calls return the whole response envelope to feature code instead of
  the `result`, which makes feature response handling unreliable.
- Only diagnostics, completion, hover, definition, and formatting have partial
  frontend entry points. References, symbols, rename, and code actions are not
  implemented.
- Servers are tracked only by language, with no workspace identity, restart
  budget, crash state, or capability-aware commands.

## Adopted boundaries

The implementation uses the following dependency direction:

```text
React UI
  -> view-only Zustand stores
  -> Workspace / Document / Editor / Language / Output services
  -> typed domain IPC clients
  -> Rust document, process, language-service, filesystem services
```

- `DocumentService` is the frontend authority for an opened document record and
  is the only path used by UI code for open/edit/save/close. The Rust Rope is the
  validated storage engine; revisions make the projection relationship
  explicit.
- `WorkspaceService` owns the runtime workspace descriptor. The descriptor uses
  a roots array even though 0.3.2 enables only one root.
- `LanguageServiceManager` owns server selection, process lifecycle, capability
  negotiation, document binding, requests, and cleanup.
- `OutputService` owns bounded user-visible channels. Persistent diagnostic logs
  remain separate from transient UI output.
- The existing `CommandRegistry` remains the single command execution route and
  is extended rather than replaced.

## Deferred debt

- True paged editable documents and removal of the full frontend document
  projection.
- User-facing multi-root workspace management.
- Advanced LSP features including semantic tokens, inlay hints, signature help,
  workspace symbols, and folding ranges.
- Complete DAP UI and a real adapter integration. DAP remains gated behind the
  completed P0 LSP acceptance criteria.
- Plugin runtime, contribution points, VSIX compatibility, marketplace, and
  permissions; all remain 0.4.0 work.

## Verification record

This section is updated as phases complete. A passing frontend build does not
count as proof of a real language server, Tauri package, process cleanup, or
manual editor regression behavior.

### Implemented

- `DocumentService` is now the UI entry point for document open, edit, save,
  close, recovery coordination, and LSP synchronization. It records path, URI,
  language, content, editor revision, saved revision, dirty/read-only state,
  UTF-8 encoding, line ending, open/save state, and the disk fingerprint.
- `WorkspaceService` exposes a runtime `WorkspaceDescriptor` with
  `singleFile`/`workspace` modes, `roots[]`, `primaryRoot`, and trust state.
- `OutputService` provides bounded and redacted Core, File System, Language
  Server, Debug Adapter, Terminal/Task, and Rust Backend channels.
- `DiagnosticsService` stores diagnostics independently of the mounted editor.
  Problems and Output now render actual service data and support navigation,
  channel selection, and clearing.
- LSP desktop calls are centralized in a typed IPC client. A static boundary
  check rejects new LSP command/event access outside `Foundation/IPC`.
- The Rust transport now uses a bounded streaming `ContentLengthDecoder`,
  routes JSON-RPC responses/errors/notifications/server requests, captures
  stderr, exposes lifecycle state and capabilities, times out/cancels requests,
  and performs shutdown/exit plus Windows Job Object cleanup.
- TypeScript and JavaScript share one server instance. Initialization includes
  the actual workspace root/folder, conservative client capabilities,
  initialization options, and settings.
- Workspace/user language-service configuration, explicit workspace trust,
  direct process spawn, and environment-value redaction boundaries are present.
- Diagnostics, completion, hover, definition, references, document symbols,
  prepare/execute rename, formatting, and code actions have command and UI
  paths. Completion and hover reject stale work; WorkspaceEdit rejects resource
  operations and overlapping edits.
- UTF-8 and UTF-16 outgoing position conversion is centralized and tested with
  Chinese, emoji, surrogate pairs, CRLF, and LF. Rust URI tests cover Windows
  drive and UNC paths.

### Release blockers and deferred debt

- Rust application code has not passed `cargo check`, Clippy, tests, or a Tauri
  build on this machine. The MSVC C++ Build Tools prerequisite remains a hard
  release blocker.
- The real server integration proves the actual TypeScript server and protocol
  flows, but not the Tauri IPC/window/editor end-to-end path. The manual 17-step
  desktop acceptance flow is therefore still unverified.
- Full-sync document changes are used in 0.3.2. Incremental sync negotiation and
  conversion of every incoming UTF-8 range remain 0.3.3 work; the TypeScript
  reference server negotiates UTF-16.
- Automatic crash restart with a five-minute restart budget is not complete.
  Manual stop/restart and bounded request lifecycle are implemented.
- Output history is bounded and redacted in memory, but persistent five-file log
  rotation and the native “open log file” action are not complete.
- WorkspaceEdit performs a full preflight before sequential saves, but durable
  multi-file rollback after an unexpected mid-save filesystem failure is not
  guaranteed.
- `AuronaEngine` no longer owns document persistence/LSP lifecycle, but remains
  large. Input, viewport, and decoration extraction should continue without
  replacing the custom editor core.
- Performance benchmark and manual IME, large-file, terminal, Git, theme, and
  window-close regressions have not been measured in a runnable Tauri build.
- The DAP gate was not met because Rust/Tauri and manual LSP acceptance remain
  blocked. No DAP UI or claims of debug-adapter completion were added.
