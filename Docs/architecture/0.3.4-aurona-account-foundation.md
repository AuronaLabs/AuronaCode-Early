# Aurona Account 桌面接入预留（0.3.4）

## 必须登记的 callback

需要在 Aurona Account 注册的 callback 地址是：

```text
http://127.0.0.1/oauth/callback
```

这是 OAuth 2.1 原生应用的动态 loopback redirect URI 注册值。Aurona Code 每次授权时只在本机回环接口监听一个由操作系统分配的临时端口，实际请求形如：

```text
http://127.0.0.1:<ephemeral-port>/oauth/callback
```

- Scheme：`http`
- Host：`127.0.0.1`
- Port：动态临时端口，不登记固定端口
- Path：`/oauth/callback`
- 不接受 `localhost`、局域网地址、通配符、fragment 或额外 path

依据原生应用 OAuth 的 loopback 约定，授权服务器匹配该注册值时允许实际运行端口变化，但仍严格比较 scheme、loopback IP、path 和 query。Aurona Account 2026-08-03 的公共客户端支持报告已确认 XAdmin 和授权服务具备这项策略；普通 Web 客户端与非回环 HTTP redirect 不受此例外影响。

Aurona Code 不使用自定义 URI Scheme，因此 Windows/Tauri 不需要注册协议处理器，也不需要 deep-link 或 single-instance 插件。Tauri 只使用 opener 在系统默认浏览器打开授权页；callback 由 Rust 的短生命周期 `127.0.0.1` listener 接收。

## XAdmin 登记建议

创建两个公开客户端，均不得生成、下发或保存 `client_secret`：

| 环境 | 客户端名称 | 类型 | Redirect URI | Scopes |
| --- | --- | --- | --- | --- |
| 开发/测试 | Aurona Code Development | Public / Native | `http://127.0.0.1/oauth/callback` | `openid profile email offline_access` |
| 正式 | Aurona Code | Public / Native | `http://127.0.0.1/oauth/callback` | `openid profile email offline_access` |

开发版与自动化测试可共享 Development client；正式版使用独立 client，以便独立撤销、审计和轮换配置。两者 callback 可以相同。0.3.4 不内置 client ID 且 feature 默认关闭；0.3.5 开放产品界面时再分别注入 public client ID。

## 实现边界

账户协议完全位于 Rust `AccountAuthService`：

1. 从 `https://auth.aurona.cc/api/auth/.well-known/openid-configuration` 读取 Discovery。
2. 强制校验 issuer 与所有端点 origin；线上端点必须为 HTTPS。
3. 生成高熵 `code_verifier`、PKCE S256 `code_challenge`、`state` 与 OIDC `nonce`。
4. 绑定 `127.0.0.1:0` 后构造带实际端口的 `redirect_uri`，再打开系统浏览器。
5. listener 只接受一次 GET、只接受 `/oauth/callback`、限制请求头为 16 KiB，并在五分钟后超时。
6. 常量时间比较 state，使用相同 `redirect_uri` 与 verifier 交换一次性 authorization code。
7. 只接受 Bearer token；从 JWKS 选择 `kid`，只允许非对称签名算法，验证签名、issuer、audience、azp、nonce、exp 与 iat。
8. 成功和失败 callback 都先校验 state；调用 UserInfo 后要求其 `sub` 与 ID Token `sub` 相同。
9. 支持 `email_verified`；头像只接受无 userinfo/fragment 的 HTTPS Aurona 域名 URL，不可信头像值会被丢弃。
10. access token 与 ID Token 只保存在内存；refresh token 只进入系统凭据库（Windows Credential Manager / macOS Keychain / Linux Secret Service）。
11. token 过期可以使用 refresh token 恢复；`invalid_grant`、401、撤销或注销会清理本地会话。应用关闭时取消 listener 并清除内存 token。

前端只有类型化 IPC 协议，没有 Store、登录按钮、账户设置、命令、侧栏入口或 Output channel。0.3.4 启动时的内部 restore 调用会被 feature policy 拦截，不访问线上服务，也不改变现有流程。

## 本地 mock 验证

Rust 自动化测试启动临时本地 OIDC Provider，并使用真实 RSA 签名/JWKS 验证以下链路：

- Discovery 与端点安全策略；
- Authorization URL、302 callback、state 传递；
- PKCE S256 verifier/challenge；
- 一次性 authorization code，重复交换返回 `invalid_grant`；
- Token、签名 ID Token、JWKS、issuer/audience/nonce；
- UserInfo 与 `sub` 一致性；
- `email_verified`、Aurona 头像域名限制；
- callback 正确路径、错误 path、`access_denied` 和失败回调 state 保留；
- production feature 在无 client ID 时保持关闭。

mock 只证明 Aurona Code 的本地协议和回调实现，不代表 Aurona Auth 线上授权已经开放或联调成功。以下内容必须等 Aurona Auth 开放后再验收：

- 线上 Discovery 元数据与真实 client ID；
- 使用 XAdmin 创建的真实 public client 验证动态 loopback 端口匹配；
- 线上 Token/JWKS/UserInfo/Revocation 的字段与错误响应；
- 真实浏览器登录、用户取消、授权撤销、Token 刷新与网络异常；
- 开发和正式客户端的独立审计记录。

本次实现验证结果（2026-08-03）：

- `cargo test --all-targets`：40/40 通过，其中 Account 专项 10/10 通过；
- `cargo clippy --all-targets -- -D warnings`：通过；
- TypeScript、Biome、桌面边界、Material 边界、smoke：通过；
- Vite production build：通过；
- Windows release executable、MSI、NSIS：均生成成功；
- updater artifact 签名：本机未配置 `TAURI_SIGNING_PRIVATE_KEY`，因此在安装包生成后停止。此项是发布密钥环境要求，不是编译或协议测试失败。

线上状态核对：2026-08-03 直接读取既定 Discovery URL 仍得到 `NOT_FOUND / 接口不存在`。因此“服务端报告已声明支持”和“线上 Discovery 已可联调”必须分开记录；在该地址返回标准 Discovery JSON 且 XAdmin 下发真实 Client ID 前，Aurona Code 不会宣称线上登录已验证。

## 0.3.5 启用清单

1. XAdmin 创建 Development 与 Production public/native clients。
2. 将 callback 精确登记为 `http://127.0.0.1/oauth/callback`。
3. 为对应构建注入 `AURONA_ACCOUNT_CLIENT_ID`，启用 Cargo feature `aurona-account`。
4. 完成真实 Aurona Auth 联调和撤销/刷新测试。
5. 再设计登录、账户资料、失败与离线状态 UI；不得让 UI 获取 raw token。
